    講義①：生成 AI とは？

    想定時間15 分 目的生成 AI の仕組み・得意不得意・ハルシネーションへの向き合い方を、ひと続きの理屈として理解する

    1. 生成 AI とは何か

    生成 AI とは、学習した大量のデータをもとに、文章・画像・ソースコードなどの新しいコンテンツを生成する AI です。GitHub Copilot でも、コードの補完、説明、修正案の提示に生成 AI が使われています。

    「確率的に最もありそうな文章などのコンテンツを作る」 仕組みになっているため、
    生成 AI が作るコンテンツは「正しさ」が保証されているわけではありません。

    2. 用語の地図：生成 AI / LLM / エージェント

    生成 AI 文章・画像・音声・コードなど、新しいコンテンツを作る AI の総称。
    LLM（大規模言語モデル） 生成 AI のうち、膨大なテキストを学習して言語（自然言語もコードも）を扱うモデル。GitHub Copilot の「頭脳」にあたる部分。
    AI エージェント ＝ LLM ＋ ツールなどの実行 与えられた目的を達成するために、自分で考えながら自律的に行動するAIのことです。ファイルの読み書き、コマンド実行、テスト実行などを自分で行い、その結果を見て次の手を決める。

    3. AI ツールの分類

    分類例特徴
    補完特化型初期 GitHub Copilot（2021）エディタ内でゴーストテキストを出すだけ（※現行 GitHub Copilot にもこの機能は内包）
    汎用 LLM チャットChatGPT / Claude / Geminiコーディング専用ではないが、コピペ運用で広く使われる
    コーディングエージェントGitHub Copilot / Cursor / Codex / Claude Code自律的にファイルを横断で読み書き・コマンド実行・テスト実行など

    2025 年以降、このコーディングエージェント型の活用が一気に広がりました。
    本日はその中の１つ、GitHub Copilot を題材に触っていきます。

    4. 得意なこと／苦手なこと（分かれ目は「指示の明確さ」）

    得意・苦手は作業の種類で決まるというより、やってほしいことがどれだけ明確に伝わっているかで決まります。生成 AI は渡された情報だけを手がかりに続きを組み立てるため、指示が明確なほど精度は上がり、曖昧なほど精度は落ちます。

    精度が高くなる（指示が明確）精度が低くなる（指示が不明確）
    入力・処理・出力が言葉になっている
    例：「1〜100 を順に出力し、3 の倍数なら Fizz、5 の倍数なら Buzz にする」    		 ゴールが一言で終わっている
    例：「いい感じに直して」「使いやすくして」
    期待する結果が具体例で示されている
    例：「20260401 を渡したら 2026/04/01 を返す」    		 判断が受け取る側に委ねられている
    例：「日付をいい形式にして」（どの形式かは書かれていない）
    守ってほしい制約が明記されている
    例：「外部ライブラリは使わず標準機能だけで書いて」    		 人間なら当然察する前提が書かれていない
    例：社内の命名規則、エラー処理の作法（下表）
    いちばん精度が落ちるのは「人間が暗黙的にやっていること」 普段の実装やレビューでは、私たちは書かなくても分かっている前提を大量に使っています。生成 AI からはこれが見えていないため、書かれていない前提は「無いもの」としてコードが出てきます。
    人間が暗黙的にやっていること（例）渡さないと、こうなる
    社内の命名規則・コーディング規約一般的には正しいが、社内規約から外れた名前・書き方で出てくる
    業務ルール（例：顧客番号は 10 桁ゼロ埋め）桁数やゼロ埋めが抜けたまま、動いてしまうコードになる
    エラー時の扱い（例外を投げるのか、戻り値のコードで返すのか）その場の一般的な作法で書かれ、既存コードと流儀が揃わない
    ログに出してよい情報／出してはいけない情報個人情報を含む値をそのままログに出力してしまう
    使ってよいライブラリ・バージョンの制約社内で未承認のライブラリを前提にしたコードが出てくる

    暗黙の前提を「情報として渡す」3 つの方法

    • 例（サンプル）を見せる：同じような処理の既存コードを開いておく、あるいは該当箇所を選択して渡します。規約を言葉で説明するより、実例を 1 つ見せるほうが早く正確に伝わります
    • 入出力を具体的に書く：「こう渡したら、こう返ってほしい」を 1〜2 組そえるだけで、狙いが一気に絞られます
    • 制約を先に書く：使ってよい範囲、守るべき形式、避けたい書き方を、指示の中に明記します

    「苦手」は固定ではありません。足りない情報を渡せば、苦手側の多くは得意側に寄せられます。逆に、渡していない前提は言い方を変えても埋まりません。

    5. 押さえておく 3 つの特性

    • 確率的応答（temperature / sampling）：同じ質問でも毎回違う答えになり得ます。再現性が無いのが原則です。
    • 学習時点のスナップショット：モデル内蔵の知識は学習が終わった時点で凍結されます。最新ライブラリ・最新 API は知らないことがあります。
    • 渡した文脈（コンテキスト）で答える：モデルの中の知識とその場で渡した情報は別物です。今書いているコードを GitHub Copilot が理解できるのは、そのコードを学習しているからではなく、開いているファイルや選択範囲が毎回コンテキストとして送られているからです。

    6. ハルシネーション

    ハルシネーションとは、生成 AI が事実ではない内容を、もっともらしい形で出力してしまう現象です。

    原因 LLM は次に来そうな語を確率で選んでいるだけで、正しさを検証する仕組みを持ちません。だから、知らないことについても「それっぽい答え」を組み立てて返します。黙って間違えるのではなく、自信のある文体で間違えるのが厄介な点です。
    必要なこと AIが生成した内容は、必ず人がチェックする

    講義②：GitHub Copilot 概要・3 モード（Ask / Agent / Plan）

    想定時間10 分 目的3 モードと Inline Chat の役割を区別し、場面に応じて選べるようにする

    GitHub Copilot Chat の 3 つのモード（2026 年 7 月時点）

    モード役割使う場面
    Ask質問・相談コードを書き換えず、概念理解・レビュー
    Agentファイル横断の読み書き・コマンド実行・テスト実行AI が対象を選び、ツールも実行する自律タスク
    Plan計画立案大きな仕様の前に「やること」を文書化、人間の承認ゲートを挟む

    加えて、Inline Chat（Ctrl+I） はエディタ内に直接小さなチャット UI を出し、選択範囲やカーソル位置の編集を即座に依頼できる軽量 UI です。

    GitHub Copilotのモードの動き

    GitHub Copilotは、コードの続きを提案するツールから、目的に応じて必要な情報を集め、作業を支援するAIへ進化しています。Ask、Agent、Planのいずれも、依頼内容に応じてワークスペース内のファイルや会話の文脈を参照し、必要な情報を集めながら回答します。違いは、自律的に情報を集めるかどうかではなく、情報を集めた後にどこまで作業を進めるかです。

    モード情報収集後の動き向いている場面
    Ask関連するコードやファイルを調べ、説明、回答、改善案を提示します。基本的にはファイルを直接変更せず、人が判断するための情報を返します。コードの理解、仕様確認、原因の相談、レビュー
    Plan関連ファイルや依存関係を調べ、変更対象、作業順序、確認方法を計画として整理します。実装前に影響範囲を確認したい場合に使います。複数ファイルにまたがる変更、実装方針の整理、作業見積もり
    Agent必要なファイルを調べたうえで、ファイル変更、ターミナル操作、テスト、修正、再確認まで進めます。失敗した場合は結果を読み、別の方法を試します。機能追加、バグ修正、テスト追加、ビルドエラーの解消
    3モードに共通するポイント どのモードも、与えられた情報だけで即答するとは限りません。目的に応じてファイル、コード、会話の文脈などを調べ、必要な情報を集めます。モードを選ぶときは、回答だけが欲しいのか、計画を作りたいのか、実際の変更と検証まで任せたいのかで判断します。

    Agentモードが実行まで進める作業例

    • 複数ファイルの機能追加：画面、API、データ処理、テストなど、関係するファイルを探してまとめて変更します。
    • ビルドエラーの解消：ビルドを実行し、エラー内容を読んで、型、参照、設定などを修正します。
    • 依存関係の調査と修正：設定ファイルやロックファイルを読み、ライブラリの不足やバージョン不整合に対応します。
    • リファクタリング：利用箇所を横断的に調べ、関数名の変更や共通処理の切り出しを行います。
    • テストの追加：既存テストの書き方を読み、変更した機能に合わせて正常系と異常系のテストを作ります。
    • ログからの原因調査：アプリケーションログやターミナル出力を読み、修正と再実行を繰り返します。
    • ドキュメント更新：実装変更に合わせてREADME、設定例、操作手順などを更新します。

    講義③：トークンと AI 利用量の説明

    想定時間10 分 目的AI とのやり取りの「単位（トークン）」と「コスト（AI Credits）」の感覚をつかむ

    トークンの正体

    • トークン：AI が文章を読み書きする際の最小単位。
    • 日本語は 1 文字あたり 1〜3 トークンを消費するのが一般的（英語の方がトークン効率は良い）
    • コンテキストウィンドウ：AI が一度に読み書きできる入力・出力の合計トークン量（主要モデルは 100K〜1M トークン規模）
    • 長いファイルや長い会話履歴を渡すほど、コンテキストウィンドウとトークン消費の両方を圧迫します
    具体例：日本語 400 文字程度の文章はおおよそ 500〜800 トークンに相当します。会話を続けるほど過去のやり取りもコンテキストウィンドウに積み上がるため、コンテキストウインドウが大きくなりすぎると AI が古い内容を「忘れた」ように振る舞うことがあります。

    AI Credits（利用量）の考え方

    2026 年 6 月 1 日に 従量課金に移行されました。 GitHub Copilot は、1 credit = $0.01 USDの課金体系です。
    利用するモデル、利用するトークン数 に応じて消費する credit が変わります。

    効率よく使うポイント

    1. コード補完は使い放題：ghost text による補完・Next Edit Suggestions は AI Credits を消費しないため、遠慮なく使ってよい
    2. Chat / Agent はクレジットを消費：1 回のやり取りごとに、入力＋出力のトークン量に応じて消費される
    3. 無駄なコンテキストを渡さない：巨大なファイル全体ではなく、必要な範囲だけを選択してから質問する
    4. プロンプトを 1 回で的確に書く：曖昧な指示で何度もやり取りするより、What/How/Why を最初から含めたほうが消費を抑えられる

    休憩（5 分）

    席に戻ったら VS Code を開いて、リポジトリのフォルダにいる状態で待機してください。

    ここからハンズオン 以降は受講者が手元で実機操作するパートです。手順どおりに進め、各ハンズオン末尾のチェックポイントで、要点だけをまとめて確認してください。

    ハンズオン①：コード補完体験

    想定時間20 分 目的GitHub Copilot のインライン補完（ghost text）を体感する 題材samples/session1/fizzbuzz_starter.py

    完成イメージ

    fizzbuzz_starter.py を実行すると、1 から 100 までの FizzBuzz が出力される。

    FizzBuzz とは：1 から N までを順に出力するプログラミング初級題材。3 の倍数なら Fizz、5 の倍数なら Buzz、3 と 5 の両方の倍数なら FizzBuzz、それ以外はその数字をそのまま出力します。 
    1
2
Fizz       ← 3 の倍数
4
Buzz       ← 5 の倍数
Fizz       ← 6（3 の倍数）
...
14
FizzBuzz   ← 15（3 と 5 の両方の倍数）

    手順 1：補完を出して確定する

    このファイルには「何をしたいか」を書いた日本語コメントだけが入っています。コードは 1 行も書かれていません。ここから GitHub Copilot に書かせます。

    # コード補完体験

# 1 から 100 までの FizzBuzz。3 の倍数なら Fizz、5 の倍数なら Buzz、
# 3 と 5 の両方の倍数なら FizzBuzz、それ以外はその数字をそのまま出力する。
    1. VS Code で samples/session1/fizzbuzz_starter.py を開きましょう
    2. FizzBuzz の説明コメント（3〜4 行目）の直下、5 行目（ファイルのいちばん下の空行）にカーソルを置きましょう
    3. def と入力して、そのまま 1〜2 秒待ちます。カーソルの先に薄いグレーの文字で fizzbuzz(): という関数名の候補が現れます。これが GitHub Copilot の提案（ゴーストテキスト）です。まだ確定していないので、ファイルには何も書き込まれていません
    4. 内容を確認しましょう。問題なければ Tab キーで確定します（Esc で却下、提案が複数あれば Alt+] / Alt+[ で切り替え）
    5. 関数名を確定すると、続けて関数の中身がまとめてゴーストテキストで提案されます。こちらも内容を確認して Tab キーで確定しましょう

    どんな提案が出てくるか

    この題材では、おおむね次のようなコードが提案されます。

    def fizzbuzz():
    for i in range(1, 101):
        output = ""
        if i % 3 == 0:
            output += "Fizz"
        if i % 5 == 0:
            output += "Buzz"
        print(output if output else i)
    上の例と一字一句同じである必要はありません output に文字を足していく書き方ではなく if i % 15 == 0: から始まる if-elif-else で提案してくる、引数付きの def fizzbuzz(n=100): になる、といった違いが出ます。講義① の確率的応答のとおり、同じ場所でも毎回同じ答えにはなりません。やりたいことが書けているかという目で見てください。

    手順 2：実行して結果を確認する

    提案には「関数を呼び出す行」が入っていないことがあります 上の提案は関数を定義しただけで、それを実行する行がありません。この状態で実行してもターミナルには何も表示されません。
    1. ファイルのいちばん下（関数の外側・インデントなし）に、作った関数を実行する 1 行を追記しましょう 
      fizzbuzz()

      補完された関数名が fizzbuzz 以外だった場合や、引数付き（def fizzbuzz(n=100): など）だった場合は、その名前・引数に合わせて書きます（例：fizzbuzz(100)）。提案の中に既に呼び出し行が含まれていた場合は、この手順は不要です。

    2. ファイルを保存しましょう（Ctrl+S）
    3. VS Code 上部のメニューから ターミナル → 新しいターミナル を選びましょう。画面下部にターミナル欄が開きます
    4. 次のコマンドを入力して Enter を押しましょう（Windows・PowerShell の場合） 
      python samples\session1\fizzbuzz_starter.py
    5. ターミナルに 1 から 100 までの出力が流れ、3 の位置に Fizz、5 の位置に Buzz、15 の位置に FizzBuzz が並んでいれば成功です

    補完を引き出すコメント

    ここまでで分かるとおり、インライン補完は直前のコメントを手がかりにコードを組み立てます。今度は自分でコメントを書いて、補完を引き出してみましょう。ファイルのいちばん下に次の 1 行を書き、Enter で改行して 1〜2 秒待ちます。

    # リストの中の偶数だけを合計する（リスト内包表記を使う）

    「何をしたいか」を具体的に書くほど、提案は狙いに近づきます。逆にコメントが曖昧だと、提案も的を外します。

    ハンズオン②：プロンプトで処理を説明させる

    想定時間20 分 目的既存コードの理解を GitHub Copilot に手伝わせる 題材samples/session1/csv_processor.py（わざと読みづらいコード）

    準備

    1. VS Code で samples/session1/csv_processor.py を開きましょう
    2. サイドバーの GitHub Copilot Chat アイコンをクリックして、チャットパネルを開きましょう
    3. モードピッカーが Ask になっていることを確認しましょう

    ステップ A：まず、ひと言だけで頼んでみる（5 分）

    Chat の入力欄に、次の 1 文だけを入力して送信しましょう。

    この処理を説明して

    「この処理」が指すのは、エディタで開いているファイル（アクティブなタブ）です。コードを範囲選択してから送れば、その選択範囲が対象になります。

    返ってきた説明を読んでみてください。それなりに読めるものは返ってきますが、何をどこまで書くかは GitHub Copilot まかせです。自分が知りたかったことが入っているかどうかは、送ってみるまで分かりません。

    ステップ B：構造化プロンプトで深掘りする（本題・15 分）

    ここが今回の本題です。ステップ A のように短く頼むと、返ってくる項目も粒度も相手まかせになります。次は、初めてこのコードを触る人が知りたいことをこちらから指定して説明させてみましょう。

    このファイルを解析し、下記に従って処理を説明して

1.目的：このファイルは何のためのものか（1～2 文）

    プロンプトの工夫ポイント

    良いプロンプト = 3 つの要素を含む

    1. What：何をしてほしいか（要約・列挙・変換）
    2. How：どんな形式で（1〜2 文、表で、箇条書きで）
    3. Why / Context：背景情報（対象ファイル、制約、推測を禁じる指示）

    悪い例：「これ何？」／ 良い例：「このファイルの主目的を 1 文で説明し、実行すると何が起きるかを箇条書きで」
