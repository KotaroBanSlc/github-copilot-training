    講義④：プロンプトエンジニアリング基礎

    想定時間10 分 目的プロンプトに何を書けば結果が安定するのかを型として押さえ、リポジトリ全体に効かせる方法まで理解する

    1. 良いプロンプトの型：5 つの要素

    第 1 回で扱った What / How / Why をもう一段細かくすると、次の 5 つに分解できます。

    世の中には CO-STAR、RTF（Role・Task・Format）など様々なプロンプトの型が提唱されていますが、「前提・役割・作業・出力形式・成功条件を明示する」という中身はどれもほぼ共通です。名前を覚える必要はありません。要素を押さえてください。

    flowchart LR
    C[Context<br/>背景・前提] --> R[Role<br/>誰として答えるか]
    R --> A[Action<br/>何をするか]
    A --> F[Format<br/>出力形式]
    F --> T[Target<br/>成功条件]
    style C fill:#0366d6,color:#fff
    style T fill:#2ea043,color:#fff
    要素書くこと書かないと起きること
    Context（前提）対象のコード・前提・制約関係ないファイルを直しに行く
    Role（役割）どういう立場で答えてほしいか粒度が読み手に合わない
    Action（作業）してほしい作業（分割する・直す・書く）説明だけで終わる／勝手に書き換える
    Format（出力形式）出力の形（箇条書き・表・差分）長文が返ってきて読むのに時間がかかる
    Target（成功条件）満たすべき成功条件「できました」の基準が人と AI でずれる

    たとえば「このコードを説明して」は Action だけの指示です。説明の粒度も観点も AI 任せになるため、長い逐行解説が返ってくることもあれば、いちばん知りたい処理に触れないこともあります。5 つを入れると次のようになります（第 1 回で使った csv_processor.py への依頼です）。

    Python を書き始めたばかりの新人に説明する先輩役として、
#file:csv_processor.py が何をするプログラムなのか説明してください。

条件:
- 1 行ずつの逐行解説にはしない
- 関数 f / g / h それぞれの役割に必ず触れる
- 専門用語（DictReader など）には 1 文の補足を付ける

「概要 → 処理の流れ → 各関数の役割」の順に、箇条書きでまとめてください。

    1 行目が Role、#file:〜 が Context、「説明してください」が Action、「条件:」の 3 行が Target、最後の行が Format です。

    結果の差がいちばん出るのは Target（成功条件） 「わかりやすく説明して」では、何をもって「わかりやすい」かが AI 任せになり、結果がぶれます。「逐行解説にしない」「f / g / h の役割に必ず触れる」のように、返ってきた説明をあとでチェックできる言葉に置き換えるのがコツです。

    全部を毎回書く必要はありません。結果が安定しないときに、どの要素が抜けているかを探すチェックリストとして使ってください。ハンズオン④のプロンプトはこの型で書かれています。

    2. カスタムインストラクション：毎回書かずに済ませる

    5 つの要素を毎回フルで書くのは大変です。このうち、どのプロンプトにも繰り返し書くことになる部分——技術スタックや規約といった前提（Context の一部）、「規約に準拠していること」のようにいつも同じ条件（Target の一部）——は、.github/copilot-instructions.md をリポジトリ直下に 1 枚置くと、そのリポジトリでの Copilot Chat の呼び出しに自動で効かせることができます。作業対象やそのタスク固有の成功条件は、これまでどおり毎回のプロンプトで指定します。

    コツは、規約を羅列するのではなく「新しく入ったメンバーに初日に説明すること」を書くことです。プロジェクトの概要・置き場所のルール・禁止事項が入っていると、Copilot の提案がそのプロジェクトのコードに寄ります。

    # リポジトリ共通の指示

## このプロジェクトについて
社内向けの契約管理 Web API。社内ネットワークからのみ利用される。
Python 3.11 / FastAPI / PostgreSQL。テストは pytest、フォーマッタは ruff（行長 100）。

## どこに何を書くか
- app/api/ … エンドポイント定義のみ。業務ロジックは書かない
- app/services/ … 業務ロジックはここに集約する
- app/repositories/ … DB アクセスと SQL はここにだけ書く
- tests/ … app/ と同じ階層構造でテストを置く

## 必ず守ること
- 型ヒント必須。識別子は英語、コメント・docstring は日本語
- SQL は必ずパラメータバインドで書く。文字列連結で組み立てない
- 接続情報・認証情報はコードに書かず、環境変数から読む
- 契約番号・氏名などの個人情報をログや例外メッセージに出さない
- 例外を except: pass で握りつぶさない
- 関数を追加・修正したら、対応する pytest のテストも追加する

## 回答の仕方
- 説明は日本語。変更の提案は差分と理由をセットで示す
- 仕様が読み取れないときは、推測で実装せず先に質問する
    運用の注意
    • 効くのは Chat 側（Ask / Agent / Plan）。コード補完（ゴーストテキスト）には効きません
    • 公式の推奨は「短く・1 項目 1 文で」。「あったら良い」ではなく「守られないと困る」ものだけに絞り、長くなってきたらテーマ別の *.instructions.md に分割する
    • lint やフォーマッタが機械的に強制できるルール（行長など）は書かない。ツールに任せる
    • 「読みやすく」のような合否を判定できない要望は、ここに書いても効きません
    • 書けば必ず守られるわけではありません。差分レビューは引き続き必須です

    ハンズオン④：リファクタリング

    想定時間25 分 目的観点を指定して、既存コードの構造だけを AI に変えさせる（振る舞いは変えない） 題材samples/session2/refactor_target.py（70 行超の単一関数、マジックナンバー、命名 NG、重複コード）

    完成イメージ

    refactor_target.py の 1 つの巨大関数 do_it が、責務ごとに分割されている状態を目指します。

    • aggregate_per_user()：ユーザーごとの集計
    • compute_bonus()：ボーナス対象判定
    • forecast_annual()：年間予測計算
    • format_ranking_line()：ランキング行のフォーマット
    • マジックナンバーが定数化（TAX_RATE = 0.10、BONUS_THRESHOLD = 100_000 など）

    関数名や分割の数は生成のたびに変わります。上に挙げたのは一例です。大事なのは責務ごとに分かれていて、意図が名前から読めることです。

    リファクタリングは「振る舞いを変えない」作業です 構造・命名・重複を整えても、実行結果は 1 文字も変わらないのが成功条件です。だからこそ、先に実行して出力を控えておくことが重要になります。

    手順

    1. VS Code で samples/session2/refactor_target.py を開きましょう
    2. まず次のコマンドを実行して、動作する状態と今の出力を確認しましょう（あとで見比べます） 
      python samples\session2\refactor_target.py
    3. GitHub Copilot Chat を Agent モード に切り替えましょう
    4. 次のプロンプト（観点指定リファクタ）を送信しましょう 
      #file:refactor_target.py を直接編集する形で、以下の観点でリファクタリングしてください。

1. マジックナンバー（10, 100000, 5, 12 など）を意味のある名前付き定数に
2. 70 行超の do_it 関数を、責務ごとの小さな関数に分割（集計 / 判定 / 整形 / 出力など）
3. 命名を PEP8 準拠かつ意図が伝わるものに
4. ランキング行フォーマットの重複を共通化
5. グローバル変数 OUT を使わず、関数の戻り値で表現
6. 分割した各関数に docstring を付け、意図が読み取りにくい箇所には
   「なぜそうしているか」が分かるコメントを添える
   （コードを読めば分かることの繰り返しは書かない）
7. 既存の振る舞いは保持（出力結果が変わらないこと）

編集後、変更点を箇条書きで説明してください。

      7 つの観点が Target（成功条件）、#file: が Context、「直接編集する形で」が Action、最後の 1 行が Format にあたります。講義④ の型がそのまま入っています。

    5. Agent モードはファイルを直接書き換えます。編集内容はエディタ上に差分（緑＝追加行／赤＝削除行）で表示されるので、まとめて Keep（保持）せず、変更のかたまりごとに中身を読んでから Keep / Undo（取り消し）を判断しましょう
    6. Keep したら、もう一度実行して出力が手順 2 と変わっていないことを確認しましょう
    7. VS Code のソース管理ビュー（左サイドバーの枝分かれアイコン）でファイルをクリックし、変更前後の差分をまとめて確認しましょう

    期待される結果

    • do_it が責務ごとの複数の関数に分割される（分割数は生成により 4〜12 個程度と幅があります。数ではなく責務ごとに分かれているかで見てください）
    • 定数 TAX_RATE、BONUS_THRESHOLD、BONUS_RATE、MONTHS_PER_YEAR などが追加される
    • 命名が改善される（例：do_it → aggregate_user_revenue）
    • 分割された各関数に docstring が付き、要所にコメントが入る
    • ソース管理ビューで差分を確認した上で、再実行しても出力が変わらない
    うまくいかない場合のヒント（クリックで展開）
    症状対処
    変更が一度に大きすぎて追えないプロンプトに「変更を 3 段階に分けて、1 段階ずつ編集してください」を追加し、段階ごとに Keep / Undo を判断する
    振る舞いが変わってしまったソース管理ビューで差分を確認 → AI に「こう変わってしまったが意図通りか？」と聞き直す
    Agent モードがファイルを大きく書き換えすぎるKeep する前に差分を確認し、かたまり単位で受け入れる。または Inline Chat（Ctrl+I）で範囲を絞った編集に切り替える

    補足：選択範囲だけ書き換えたい場合（Inline Chat、Ctrl+I）

    do_it 関数の中の特定ブロックだけ手早く書き換えたい場合は、その範囲を選択して Ctrl+I を押します。Chat パネルを開かずに、エディタ内に直接小さな入力欄が現れます。たとえば refactor_target.py の「出力フォーマット」の for ループ（72〜80 行目）を選択して、次のように依頼できます。

    選択したランキング行の組み立てを、format_ranking_line(rank, user_id, info) という関数に切り出してください。
引数には rank に i + 1、user_id に k、info に v を渡してください。

    行番号と変数名はリファクタリング前の refactor_target.py のものです。手順 5 で Keep した後は関数が分割されて行番号がずれるので、この補足を試す場合はソース管理ビューで変更を破棄して元に戻してから行ってください。

    Inline Chat と Agent の使い分け（2026 年 7 月時点）

    状況おすすめ
    関数 1 つ・選択範囲のリファクタInline Chat（Ctrl+I）
    単一ファイル内の網羅的リファクタAgent モード（ファイル指定で投入）
    複数ファイルにまたがる変更Agent モード
    不確実性が高く設計から立てたい大きな変更Plan モード → Agent モード
    Agent モードはファイル横断で書き換えます。Keep する前の差分レビューは必須です。Inline Chat は選択範囲に対する即時編集に最適で、Accept / Discard でその場で採否を決められます。

    Vibe Coding とは

    生成AIを利用し雰囲気で実装を行うことを指しています。要求だけ伝えて、仕様や設計、実装はAIに任せるイメージです。

    完成イメージ

    • 矢印キー操作 ＋ スペースでハードドロップ
    • スコア表示・ゲームオーバー画面
    • index.html をダブルクリックするだけで動く（追加インストール不要）

    手順

    1. 教材リポジトリ（github-copilot-training）を開いたまま、GitHub Copilot Chat を Agent モード に切り替えましょう。VS Code でフォルダを開き直す必要はありません（出力先はプロンプトで指定します）

    • コードを読まない
    • 自然言語だけで指示する

      • これが Vibe Coding 後の実務での最低限のレビュー量です
    2. 読み返したあとで、自分の中で振り返りましょう

    Vibe Coding が向いているタスク

    「まだ形が決まっていないもの」「壊れても影響が小さいもの」に強いスタイルです。

    • 方向性の探索：案を複数まとめて形にして、どれが良いか手触りで比べる
    • アイデアを形にする：頭の中のイメージを動くものにして、関係者と同じ画面を見ながら議論する
    • MVP・プロトタイプ開発：作り込む前に検証し、本実装に進むかどうかを判断する
    • ツール作成：定型作業を片付ける自分用の小さな道具や、使い捨てスクリプト
    • 学習・キャッチアップ：AI の得手不得手を体感し、任せどころの感覚をつかむ

    逆に、長く保守するコード・他人が引き継ぐコード・個人情報や決済など事故のコストが大きい領域には向きません。用語の生みの親である Andrej Karpathy 自身も「週末の使い捨てプロジェクト」向けと位置づけており、業務に持ち帰るときは差分を読んでレビューする段階を必ず挟んでください。「読まずに受け入れる」のをやめた時点で、それは Vibe Coding ではなく通常の AI 支援開発です——今日ここまでのハンズオン①〜⑥が、まさにそちらのやり方でした。
