    講義⑥：Plan モードの位置づけ

    想定時間15 分 目的Plan モードを「設計を専門にした Agent」として捉え、規模と不確実性で Agent と使い分けられるようにする

    Plan モードとは何か

    Plan モードは、GitHub Copilot Chat に組み込まれた計画立案に特化したチャットモードです。コードは書かず、設計と段取りだけを詰めて plan.md という計画書にまとめてくれます。

    ひとことで言えば、設計を専門にした Agent です。Agent モードに「そうじゃないんだよなあ」と何度も出し直させた経験がある方は、その手戻りを減らすための仕組みだと考えてください。

    Plan モードと Agent モードの違い

    項目PlanAgent
    出力計画書（plan.md）コード変更
    実行コードは触らないファイルを書き換える、コマンドを実行する
    質問積極的にこちらに質問してくる推測で進める
    適合するタスク仕様が曖昧な大きな変更仕様が明確な変更
    引き継ぎStart Implementation で Agent に渡す—
    Plan は、後になって「思っていたのと違う」となるのを防ぐための仕組みです。Agent が推測で進めてしまう部分を、先に質問として表に出させます。

    仕様 → 実装の 2 段階フロー

    今日のハンズオンで回すのは、次の流れです。plan.md を人がレビューするステップが真ん中に入るところがポイントです。

    flowchart LR
    A[要件] --> B{規模・不確実性}
    B -- 小さい・明確 --> E[Agent モード]
    B -- 大きい・曖昧 --> C[Plan モード]
    C --> D[plan.md]
    D --> R[人間レビュー]
    R -- OK --> S[Start Implementation]
    S --> E
    E --> F[実装]
    F --> G[コードレビュー]
    style C fill:#0366d6,color:#fff
    style E fill:#2ea043,color:#fff

    計画に不足があれば、実装に進む前に「plan.md を更新して、〇〇を追加してください」と戻せます。コードが書かれる前に軌道修正できるので、Agent に直接投げて作り直させるより手戻りが小さくなります。

    いつ Plan を使うべきか

    公式ドキュメントでは、Plan は「複数ステップにわたる作業を、コードを書く前に分解して固める」ための機能とされています。判断の目安は次の 3 つ。1 つでも当てはまれば Plan → Agent、どれにも当てはまらなければ Agent 直行で構いません。

    #目安例
    1変更が複数ファイル・複数レイヤーに跨るスキーマ・API・フロントが連動する新機能
    2要件に未決定事項が残っている「保存形式は？」「エラー時は？」と質問が浮かぶ状態
    3間違えたときの手戻りが大きいスキーマ変更、新規プロジェクトの立ち上げ、公開 API の変更

    計画は実装より直すのが圧倒的に安いので、Plan に入ったらすぐ実装に進まず、計画への質問・修正に時間を使うのがベストプラクティスとされています。

    ペアプロの進め方

    今日のペアプロは、ドライバとナビゲーターに役割を分ける古典的なスタイルではなく、2 人が同じ課題にそれぞれチャレンジして、過程を共有し合うスタイルで進めます。

    やること具体的には
    各自でチャレンジ基本は自分の PC で同じ課題に取り組む。プロンプトも修正方針も、自分で考えて投げてみる
    共有タイム1 つの課題が終わる（または詰まる）ごとに、どんなプロンプトを投げたか／どんな問題が起きたか／どう解決したかを画面を見せながら共有する
    一緒に試行錯誤詰まったら抱え込まず声を掛ける。相手のプロンプトを自分の環境で試してみるのも歓迎
    • 思考発話（think-aloud）：「今こう考えている」「この提案は怪しい気がする」を口に出しながら進めます。黙々と進めるとペアプロになりません
    • 共有タイムでは成功例だけでなく失敗例を見せ合ってください。「AI にこう騙された」が一番の学びの素材です
    • 1 台しか動かない場合は、1 台を課題ごとに交代で使い、見ている側は差分レビューと思考発話で参加します

    3 人 1 組になった場合も進め方は同じです。共有タイムを 3 人で回し、全員が自分の試行錯誤を話してください。

    今日の主役は「共有」です 同じ課題でも、投げるプロンプトも、返ってくる提案も、人によって違います。その違いこそが今日の教材です。相手のやり方から自分のプロンプトの改善点に気づき、2 人で試行錯誤する時間を通じて「チームで AI 駆動開発を進める」イメージを持ち帰ってください。

    使うプロンプト

    そのままコピーして使えるプロンプトを、課題ごとに用意しています。コピーして貼るだけで終わらせず、返ってきた差分を自分で読み、共有タイムでペアの結果と見比べるところまでをセットにしてください。アレンジして投げてみるのも歓迎です。

    B1：原因特定 ＋ 類似バグの横断探索（Agent モード）

    まず再現します。ブラウザで完了マーク付き（チェック済み）の TODO、たとえば「設計書を書く」の削除ボタンを押し、確認ダイアログで OK を押すと、アラートに「not found」と表示されて削除できません。未完了の TODO は問題なく削除できます。

    再現できたら、Agent モードで次のプロンプトを送ります。

    samples/session3/todo-app-buggy 配下の TODO アプリを修正してください。

## 現状
ブラウザで完了マーク付きの TODO（completed=1）を削除しようとすると、
アラートに「not found」と表示され、削除できません。

## 期待
完了状態にかかわらず TODO が削除できる。

## 依頼
1. 原因を特定し、修正パッチを提案してください
2. 同じ DELETE エンドポイントに他の潜在バグがないか確認してください
3. 検索や更新エンドポイントなど、他にも類似のバグがないか
   横断的にチェックしてください。ただし見つかったものは
   修正せず、一覧で報告だけしてください（この後の課題で自分で直します）
4. 修正の単体テストも提案してください（pytest）

    1 行目のようにディレクトリを指定しておくと、Copilot が配下の server.py や public/ のファイルを自分で探して読んでくれます。

    3 番目の依頼を書くかどうかで結果が変わります 「他にも類似のバグがないか横断的に」と書かないと、Agent は示した 1 件だけを直して終わります。第 2 回の講義④で扱った Target（成功条件）を書くかどうかの違いが、そのまま出るところです。プロンプトに書くか書かないかで、AI の探索範囲が変わります。あわせて「修正せず報告だけ」と添えているのは、書かないと Agent が B2 に相当するバグまでこの 1 往復でまとめて直してしまうからです。探索の範囲だけでなく、どこまで手を動かしてよいかもプロンプトで制御できます。

    B2：バリデーションをどこに入れるか（Plan → Agent）

    編集ダイアログでタイトルを空文字（または半角スペースのみ）にして保存すると、そのまま保存できてしまいます。新規追加はサーバ側で弾いているのに、更新は弾いていないという状態です。

    「サーバとフロントのどちらにバリデーションを入れるか」という設計判断があるので、Plan モードで方針を確認してから実装するのが向いています。

    AI にコードレビューさせる

    修正が一段落したら、その修正を PR に出すつもりで AI にセルフレビューさせます。ペアの目に加えて、もう 1 つ観点を足す使い方です。

    /review
samples/session3/todo-app-buggy 配下の server.py にある
「完了済み TODO が削除できないバグ」に対する修正 PR を
作るとして、以下の観点でセルフレビューしてください。

1. 修正は最小限か（不要なコード変更がないか）
2. テストケースは妥当か（境界値・異常系を含むか）
3. 既存の他エンドポイントに影響しないか
4. ドキュメント更新は必要か

指摘は重大度（high / medium / low）付きで、修正案も添えてください。

    1 行目の /review はコードレビューを依頼するビルトインのスラッシュコマンドです。取り組んだ課題に応じて「完了済み TODO が削除できないバグ」の部分を差し替えて使ってください。

    AI レビューは「人のレビューの前段」に置く AI のレビューは見落としを拾う網としては優秀ですが、重要度の判断は人がやる必要があります。「high と言われたが実は許容範囲」「low と言われたが業務上は致命的」は日常的に起きます。実務では PR を出す前に /review を通し、そのうえで人のレビューに回すのが現実的な使い方です。

    • B1 が直り、完了済み TODO をブラウザから削除できる（削除すると一覧から消える）
